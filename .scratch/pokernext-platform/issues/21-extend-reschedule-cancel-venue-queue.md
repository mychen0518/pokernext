# 21: 續住、入住前改期、取消流程與琪琪行程異動佇列

**What to build:** 會員只在本次已有效 Check-in、尚未退房且尚未確認結算時才能申請續住；未入住時「修改行程」是入住前改期並沿用原 ID；入住前「取消」先顯示取消中，琪琪在行程異動佇列「開始執行」→ 在天城辦妥後「已完成」，平台立即顯示已取消並歸檔；一般續住／改期結果仍須管理者核對。

**Blocked by:** 18（天城合作端帳號、閒置鎖定、五類分項授權與可見範圍）、20（現場事實事件與服務生命週期投影）

**Status:** ready-for-agent

**UI:**
- Surface: 玩家端（申請入口）＋ 合作端（行程異動工作台）＋ 管理端（核對）
- Page type: 合作端 DESIGN.md §3.2 案件頁
- Reference: `docs/design/references/partner-change-requests.png`
- Prototype: `#/player/trips/TR-260911-028`（申請）、`#/venue/changes/CHG-260911-006`、`#/admin/trips`；actions `requestChange`, `withdrawChange`, `startChange`, `completeCancel`, `reportChange`, `verifyChange`
- Components: 玩家端 Modal（續住／改期／取消三種表單）；合作端 Tabs（待開始／執行中／待內部核對／已完成／已撤回，帶計數）、ListPanel、DetailPanel、split（目前住宿／申請內容 vN）、Stepper（申請已收到／開始執行／已完成）、Checkbox（已在天城系統完成取消）、Radio（全部／部分／無法辦理）、Button/primary（開始執行／已完成／送出回報）
- States: 玩家端三種文案分別為「取消中，等待回覆」「執行取消行程中」「已取消」；合作端 DetailPanel 底部顯示「玩家端目前顯示：…」；取消類與一般異動的完成門檻不同（取消：勾選後才可按已完成；一般：回報後等管理者）

- [ ] 續住三條件任一不成立時申請被拒（三個反例各一）；成立時可申請
- [ ] 未入住時修改整趟日期到另一個日期仍沿用原 ID、不變成取消＋新增
- [ ] 入住前取消後客戶端顯示「取消中，等待回復」，不是已取消
- [ ] 琪琪按開始執行時重查最新需求版本；客戶端顯示「執行取消行程中」
- [ ] 琪琪按已完成時必須涵蓋本次取消的所有有效住宿確認單（含接續單）；無法涵蓋則維持待處理並記原因
- [ ] 取消完成直接生效、不等管理者第二次批准；一般續住／改期結果須管理者核對後才更新預訂單（一正一反）
- [ ] 取消歸檔後退款等獨立待辦仍可見
- [ ] 天城批准範圍與玩家接受範圍不一致時分別保存並設定跟進期限；玩家拒絕部分核准後由管理者辦理外部取消，不直接標成天城已取消
- [ ] 佇列顯示待開始／執行中／結果已回報／撤回；同一案件的開始與撤回只允許一個有效結果，重送不重複作業或通知（併發測試）
- [ ] 取消案件的「已完成」按鈕在未勾選「已在天城系統完成取消」時 disabled；一般異動沒有「已完成」按鈕，只有「送出回報」

**Notes:** 5 晚只訂成 3 晚的保留釋放與退分屬第 25 票。

原型的異動案件階段（參考，不是期望值來源；與上方驗收條件衝突時以驗收條件為準）：
`pending → in_progress → reported → done`、`pending → withdrawn`；取消類
`in_progress → done` 直接產生「已取消」的來源事件，不經管理者。案件流程用
`packages/domain` 的 `transition(state, event)`（ADR-0001）。
