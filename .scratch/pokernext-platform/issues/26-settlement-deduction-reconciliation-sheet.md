# 26: 玩家確認結算、正式扣分、住宿兌換核對單與天城「雙方已對齊」

**What to build:** 會員在正式結算流程查看有效版本並按「確認本次結算」，此時才形成截止快照與正式扣分；扣分後系統自動產生住宿兌換核對單，琪琪在天城端核對該單該版本後按確認記為「雙方已對齊」；對齊只是人工交叉確認，不改 POKERNEXT 帳目、不推定押金已退；更正走關聯調整單。扣分與核對單在同一張票完成，不留「扣了分沒有核對單」的過渡狀態。

**Blocked by:** 25（積分保留與可用額（送訂暫時保留→正式保留）＋ 住宿需求預覽）

**Status:** ready-for-agent

**UI:**
- Surface: 玩家端（確認結算）＋ 合作端（住宿兌換核對）
- Page type: 玩家端 Modal 於行程詳情；合作端 DESIGN.md §3.2 案件頁
- Reference: `docs/design/references/partner-change-requests.png`
- Prototype: `#/player/trips/TR-260911-028`（settlement Modal）、`#/venue/recon`；actions `confirmSettlement`, `venueAlign`, `raiseDiff`
- Components: 玩家端 Modal（KeyValueList：確認單、實際住宿、可用積分、兌換晚數×25,000、已付押金、預計應退）＋ Button/primary（確認本次結算）；合作端 ListPanel（核對單＋Badge 待核對／雙方已對齊）、DetailPanel（KeyValueList、逐晚分配 DataTable：晚／日期／兌換／押金／應退）、split（單據餘額快照／目前最新帳面）、Button/primary（確認：雙方已對齊）、Button/secondary（提出差異）
- States: 確認前內容變更 → Modal 顯示「請重新查看」並鎖按鈕；未確認核對單顯示提出時間與已等待時間，不顯示逾期；原單已對齊＋調整待核對 → 兩個 Badge 並列

- [ ] 扣分唯一觸發點是本人確認有效結算版本；酒店確認、保留成立、提醒、任務回覆、天城確認都不觸發扣分（各一反例）
- [ ] 確認前內容變更 → 要求重新查看；結算確認時來源版本同時更新（併發測試）→ 拒絕、不以舊版本扣分
- [ ] 離境前即可辦理結算；確認後的正常晚到積分入原行程與餘額但不重開兌換、不追加退款
- [ ] 帳面 60,000 保留 50,000 → 正式扣 50,000 並解除對應保留 → 餘額 10,000，保留不被再扣一次
- [ ] 核准的來源更正使帳面為負：保留真實差額與差異單，可用顯示 0、限制新兌換，不產生現金欠款
- [ ] 扣分完成後自動產生核對單，含會員／行程／酒店預訂編號、逐晚日期、每晚積分、兌換晚數、本次扣分、結算前後餘額與版本
- [ ] 核對單有「單據餘額快照」與「目前最新帳面／保留／可用額及讀取時間」兩分區；後續入帳不覆寫快照
- [ ] 琪琪確認後該單該版本為「雙方已對齊」；確認不修改任何積分帳目；對齊不推定押金已退、餘額一致或 API 回寫
- [ ] 同一單同一版本只生效一次：重複按、網路重試、兩人同時確認（併發測試）都回既有結果；回應中斷後可查已保存結果
- [ ] 未確認的核對單持續保留並顯示提出時間與已等待時間；不顯示逾期、不自動確認／取消／退分（可控時鐘）
- [ ] 已確認核對單需更正時另開關聯調整單只核對差額；原單原值、確認者、時間、版本不變；行程摘要顯示「原單已對齊、調整待核對」
- [ ] 零扣分或無應退也走完整核算呈現、玩家確認與天城核對，但不建立零元實退
- [ ] 核對單詳情有「快照」與「目前最新」兩分區並各自標時間；逐晚分配表每晚都顯示兌換／押金／應退三欄
