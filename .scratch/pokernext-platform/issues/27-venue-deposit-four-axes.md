# 27: 天城押金：應付／實收／應退／實退四軸與差異案件

**What to build:** 會員只對積分不足以支持的完整晚數繳付押金；掃碼報到後看到本次應付並直接以韓元現金交給琪琪；琪琪按「已收到押金」記實收；整晚兌換成功且該晚已實付時產生應退；琪琪實際退款後按「已退還押金」；應退與實退完全一致且對應同一有效退款案件版本才可標記已退還，否則進差異案件。平台只記錄事實，不收不付不墊款。此票之前系統沒有任何退款路徑。

**Blocked by:** 19（到場短效 QR 與櫃檯報到防重（含人工核對入口））、26（玩家確認結算、正式扣分、住宿兌換核對單與天城「雙方已對齊」）

**Status:** ready-for-agent

**UI:**
- Surface: 合作端（收取／退還）＋ 玩家端（本人確認）＋ 管理端（唯讀＋差異）
- Page type: 合作端 DESIGN.md §3.2 作業頁（報到頁右欄）＋ 總覽頁 DataTable（押金紀錄）
- Reference: `docs/design/references/partner-checkin.png`（右欄押金收取）
- Prototype: `#/venue/checkin/TR-260911-028`、`#/venue/deposits`、`#/venue/deposits/TR-260908-021`、`#/player/trips/TR-260911-028`；actions `collectDeposit`, `refundDeposit`, `confirmPaid`, `confirmReceived`, `raiseDiff`
- Components: AmountDisplay（應收）、InfoBox（收款方：天城 PokerRoom）、Input 帶 KRW 前綴（實收）、DateInput（收款時間）、Button/primary（已收到押金／已退還押金）、Tabs（待收取／待住宿結算／待核對／待退還／已退還／差異）、DataTable/regular（應收／實收／應退／實退四欄 tabular-nums）、depositAxis 列（StatusDot 四軸）、玩家端 Button/primary（我已支付／我已收到）、Button/secondary（押金紀錄需要核實）
- States: 實收 0 或與應收不符 → Toast/error 且不寫入；應退≠實退 → 拒絕並引導「轉差異案件」；玩家未確認 → StatusDot/warning「待本人確認」但不顯示「未付款」

- [ ] 應付＝積分不足晚數 × 每晚押金（預設 KRW 300,000）；有積分支持的晚數不計；頁面顯示逐晚分配
- [ ] 琪琪記實收含實際金額、實際收款時間、收取人；收款時間與輸入時間分開保存；只有押金收退權的帳號可操作，只有報到權者被拒
- [ ] 會員本人的「實際支付／實際收到」確認是獨立一軸；未確認不代表未付款、不重收、不重退
- [ ] 整晚兌換成功且該晚已實付 → 該晚應退；已住宿但積分不足的該晚不退
- [ ] 應退＝實退且同一有效退款案件版本 → 可標已退還；少退、多退、錯人、錯行程 → 建立差異案件；沒有任何 API 能調低應退額或建立「部分完成」狀態（一正一反）
- [ ] 收款／退款請求重試（併發測試）只生效一次；回應中斷後先查已保存結果
- [ ] 每行程押金獨立：A 行程應退不能抵 B 行程
- [ ] 已付押金但未酒店入住即取消：仍依實收紀錄建立退款案件
- [ ] 管理者／財務／Platform admin 只能查看與提出核實，呼叫收取／退還 API 被拒
- [ ] 押金紀錄標示為非公司資金流；財務報表不把它算進收入、退款、墊款或服務費
- [ ] 會員能從「押金紀錄需要核實」入口提出疑問，送出只建案件、不改狀態
- [ ] 現金僅韓元、無收據編號與附件
- [ ] 四軸（收取／退款依據／退還／本人確認）各自一列 StatusDot，不合併成單一狀態色；管理端與員工端沒有收取／退還按鈕

**Notes:** G07：特殊費率與已離島後的錯誤善後未定；首版不開正常部分退款。

原型的押金決策（參考，不是期望值來源；與上方驗收條件衝突時以驗收條件為準）：

- 四軸文字標籤：收取（無須／待收取／已收取）、退款依據（待住宿結算／待玩家確認／
  待天城核對／應退 n／無應退）、退還（待退還／已退還）、玩家現金確認（待本人確認／
  已確認）。
- 原型的退款公式 `min(兌換晚數, 已付押金晚數) × 300,000` 是簡化版：它不檢查是否為
  「同一晚」既兌換又實付。以本票「整晚兌換成功且該晚已實付 → 該晚應退」逐晚判定為準。
